# AGENT.md — мастерская 3D-моделей для Creality K1C

Точка входа для любого агента. Прочитай этот файл целиком, прежде чем что-то делать в проекте.

## Назначение

Проект для разработки, хранения и доработки 3D-моделей, которые печатаются на Creality K1C. Работа ведётся вместе с ИИ-агентом.

Модели выкладываются **бесплатно для всех** по лицензии CC BY 4.0, поэтому репозиторий публичный. У популярных моделей есть варианты (например, органайзер на 2, 3 и 4 устройства), чтобы каждый выбрал подходящий. Описания пишем для человека со стороны: он должен понять, что это, подойдёт ли ему и как это напечатать, не читая код.

Цель: по любой модели в любой момент понятно — что это и зачем, как она выглядит и какого размера, из чего и как её печатать, из какого кода она получена, какая версия актуальная и чем версии отличаются.

Репозиторий: <https://github.com/iruch/-crealityk1c>. Правила работы с ним — в разделе «Git».

## Язык

**Всё на русском:** общение с пользователем, документация, комментарии в коде, сообщения коммитов. Латиница — только там, где без неё никак: имена файлов и папок (slug), идентификаторы в коде, технические термины и названия программ.

## Оборудование и окружение

- **Принтер:** Creality K1C — область печати 220 × 220 × 250 мм, закрытый корпус, директ-экструдер, закалённое сопло 0.4 мм, хотэнд до 300 °C, стол до 100 °C.
- **Слайсер:** Creality Print 7.3 (установлен локально).
- **Нити:** список материалов и цветов — в [FILAMENTS.md](FILAMENTS.md).
- **Node.js 24** — на нём скрипты из `tools/`.
- **Python** — только через `uv`, в систему не ставится. В начале каждого `.py`-генератора есть блок `# /// script` со списком зависимостей. Поэтому достаточно `uv run <скрипт>.py`: uv сам подтянет Python и библиотеки.

Заметки агенту по этой машине:
- `uv run` спотыкается о собственную ссылку на Python 3.14. Обход: указать интерпретатор явно — `uv run --python "$APPDATA/uv/python/cpython-3.14.8-windows-x86_64-none/python.exe" <скрипт>.py`.
- Если вывод Python идёт в pipe, выставлять `PYTHONUTF8=1`. Иначе кириллица и знаки вроде «×» падают с ошибкой кодировки cp1251.

## Структура проекта

```
README.md            — витрина репозитория для человека
LICENSE              — полный текст CC BY 4.0, не редактировать
AGENT.md             — этот файл: назначение, правила, контракт работы агента
CLAUDE.md            — подключает AGENT.md для Claude Code (не редактировать по существу)
.gitignore           — что не попадает в git (в т. ч. содержимое inbox/)
.gitattributes       — бинарные форматы и окончания строк
REGISTRY.md          — реестр всех моделей
FILAMENTS.md         — какие нити есть в наличии
templates/           — шаблоны документации
inbox/               — сюда пользователь кладёт новые и обновлённые файлы
tools/               — общие скрипты проекта (рендер видов и т. п.), не относящиеся к одной модели
models/
  phone-stand/                 — одиночная модель: папка = slug
    README.md
    v1/
      phone-stand-v1.3mf       — проект для печати
      src/                     — код, из которого модель сгенерирована
      img/                     — картинки видов
      ...                      — прочее: STL, STEP, фото, чертежи, референсы
  lil-solid-organizer/         — семейство: одна модель в нескольких вариантах
    README.md                  — общее описание и таблица вариантов
    src/                       — общий генератор всех вариантов
    lil-solid-organizer-2-devices/   — вариант: папка = slug варианта
      README.md
      v1/
        lil-solid-organizer-2-devices-v1.3mf
        img/
    lil-solid-organizer-3-devices/
    ...
```

Главное правило: **всё, что относится к модели, лежит в её папке** — 3mf, код, картинки, экспорты, референсы. Ничего, относящегося к конкретной модели, не валяется в корне или в `tools/`.

- **slug** — имя латиницей в kebab-case, которое само говорит, что это. Номеров и ID нет. У варианта slug = slug семейства + суть варианта: `lil-solid-organizer-2-devices`.
- **Даты** — в формате `YYYY-MM-DD`. **Единицы** — мм, °C, г, минуты/часы.

- В конце README каждой модели, варианта и семейства есть раздел «Лицензия» (см. шаблоны). Так человек, открывший модель по прямой ссылке, сразу видит условия.

## Одиночная модель и семейство

- **Одиночная модель** — одна папка `models/<slug>/` с `README.md` по шаблону [templates/MODEL.md](templates/MODEL.md). Код лежит внутри версии: `vN/src/`.
- **Семейство** — модель, у которой есть варианты (на разное число устройств, разного размера и т. п.):
  - `models/<семейство>/README.md` по шаблону [templates/FAMILY.md](templates/FAMILY.md). В нём общее описание, всё, что одинаково у вариантов (посадочные места, печать, исходники), и таблица вариантов с картинками.
  - `models/<семейство>/src/` — один параметрический генератор на все варианты. Вариант задаётся параметром командной строки, а не копией скрипта.
  - Каждый вариант — подпапка `<семейство>-<суть>/` со своим `README.md` (тот же шаблон MODEL.md, но короче: только то, что отличает вариант) и своими версиями `vN/`.
- Одиночная модель становится семейством, как только у неё появляется второй вариант.

## Что обязательно есть у каждой модели (и каждого варианта)

1. `README.md`: описание нормальным человеческим языком, габариты, параметры печати, как получить файл, история версий.
2. В каждой версии `vN/`:
   - файл `<slug>-vN.3mf`;
   - код генерации, если модель сделана кодом: в `vN/src/` у одиночной модели, в `src/` семейства — у варианта;
   - картинки в `img/`:
     - `iso.png` — общий вид в 3D с подписью габаритов;
     - `front.png`, `left.png`, `right.png`, `top.png` — проекции спереди, слева, справа и сверху с размерами;
     - `filled.png` — модель с содержимым, если в неё что-то кладут или ставят (органайзеры, держатели, подставки). Это первая картинка в README: человек сразу видит, как вещь выглядит в деле;
     - `preview.png` — миниатюра из 3mf (`Metadata/plate_*.png`), если слайсер её туда положил.
3. Строка в [REGISTRY.md](REGISTRY.md).

### Картинки

Картинки делает скрипт, вручную их не рисуем. Если скрипт с чем-то не справляется, дорабатываем скрипт.

```bash
npm install --prefix tools          # один раз, ставит зависимости
node tools/render-3mf.mjs <папка модели>/vN/<slug>-vN.3mf <папка модели>/vN/img --name "<Название>"
```

Опция `--color "#RRGGBB"` задаёт цвет модели на картинках, например цвет нити, которой её печатают. Скрипт также выводит габариты и объём тела. Их берём в README, а не меряем вручную.

#### Картинка с содержимым

- **Содержимое строит генератор модели**, а не скрипт картинок: только генератор знает, где какое гнездо. Для этого у генератора есть режим `--filled`. Он собирает сцену: сама модель плюс условные предметы на своих местах (устройства, пачки, кабель…). Каждый предмет — отдельный объект 3mf со своим цветом (`basematerials`, `displaycolor`).
- **Предметы рисуем упрощённо:** простые формы и спокойные цвета, без логотипов и попыток изобразить реальность. Размеры берём из тех же параметров, что и гнёзда. Если реальный размер неизвестен (например, высота пачки), ставим примерный и помечаем это в коде.
- **Рендер:** `node tools/render-3mf.mjs <сцена.3mf> <папка модели>/vN/img --filled --name "<Название>"`. Получится `filled.png`: общий вид чуть сверху, сама модель серая, как на остальных картинках, а предметы — в своих цветах.
- **Сцена — не модель для печати.** Её не коммитим (`*-filled.3mf` в `.gitignore`), всегда можно получить заново.

## Версионирование

- Версии — целые числа: `v1`, `v2`, `v3`… У каждого варианта семейства своя нумерация.
- Модель, пришедшая в проект, всегда начинается с `v1` — даже если до проекта у неё были свои номера (например, файл назывался `_v5`). С неё всё и начинается: прошлые итерации в историю не переносим.
- Новый вариант — это не новая версия: он начинается со своей `v1`.
- **Любое изменение геометрии или настроек печати = новая версия.** Новая папка `vN+1/` создаётся копированием предыдущей и уже потом меняется. Папка прошлой версии остаётся нетронутой.
- Если поменялся общий генератор семейства, новая версия появляется у тех вариантов, у которых изменилась геометрия. Код старых версий остаётся в истории git.
- Правка только текста документации или кода без изменения геометрии — не новая версия.
- Старые версии **не удаляются и не перезаписываются**. Git хранит историю, но версии всё равно лежат отдельными папками: любую можно сразу открыть в слайсере и сравнить с другой, не копаясь в истории коммитов.
- Неактуальную модель целиком переводим в статус «архив», а не удаляем.
- В `README.md` модели — таблица «История версий»: что изменилось и почему, напечатана ли версия и как себя показала.

### Статусы

| Статус | Значение |
|---|---|
| черновик | ещё не печаталась |
| на проверке | напечатана, проверяется в деле |
| рабочая | проверена, можно печатать |
| архив | больше не используется, хранится для истории |

## Реестр

[REGISTRY.md](REGISTRY.md) — одна строка на каждую модель, которую можно напечатать: одиночную модель или вариант семейства. В строке: название со ссылкой, кратко назначение, актуальная версия, габариты, материал/цвет, статус, дата обновления. Реестр обновляется в том же шаге, что и модель — они не должны расходиться.

## Git

- Работает один человек. Ветка одна — `main`. Других веток, pull request'ов и ревью нет.
- Агент коммитит и **сразу пушит в `main`** по завершении каждой задачи: новая модель, новая версия, правка документации или скриптов. Отдельно спрашивать разрешения на коммит и пуш не нужно.
- Один коммит — одно законченное изменение. Файлы модели, картинки, README и строка реестра идут в одном коммите.
- Сообщение коммита — на русском, в формате `<область>: <что сделано>`. Область — папка модели, варианта или семейства, `документация` или `инструменты`. Если нужно объяснить «почему», то после пустой строки идёт тело сообщения. Примеры:
  - `phone-stand: добавлена v1`
  - `lil-solid-organizer: варианты на 2 и 3 устройства`
  - `lil-solid-organizer-4-devices: v2 — стенка толще на 0.8 мм, v1 треснула на изгибе`
  - `инструменты: рендер видов с размерами`
- Историю не переписываем: никаких `push --force`, `rebase` и `commit --amend` для уже запушенных коммитов.
- В git не попадает: содержимое `inbox/`, временные файлы, `__pycache__`, виртуальные окружения, `node_modules`.
- GitHub не принимает файлы больше 100 МБ. Если файл больше 50 МБ, агент предупреждает пользователя до коммита.
- Репозиторий публичный: в него не кладём ничего личного (пароли, адреса, документы).

## Контракт работы агента

### Общение
- Агент не придумывает назначение модели, материал или результат печати. Чего не знает — спрашивает. Неподтверждённое помечает как неподтверждённое.
- После любой работы агент коммитит и пушит её (см. «Git») и коротко отчитывается: что создано или изменено, какие файлы, что осталось открытым.

### Новая модель (файлы в `inbox/` или в чате)
1. Изучить файлы: габариты, число объектов и пластин, настройки печати из 3mf (материал, слой, заполнение, поддержки), код, если он есть.
2. Показать пользователю, что удалось понять, и **спросить**: что это, для чего, где и как используется, каким материалом и цветом печатать, были ли проблемы.
3. Придумать slug, создать `models/<slug>/v1/`, перенести туда файлы (из `inbox/` — переносом, не копией).
4. Сгенерировать картинки видов.
5. Написать `README.md` по шаблону и добавить строку в реестр.

### Новая модель, которую разрабатывает агент
1. Уточнить задачу: назначение, ключевые размеры, ограничения, материал.
2. Написать генератор (параметры — в начале файла, с комментариями; блок `# /// script` с зависимостями), получить модель, сделать картинки.
3. Документировать так же, как любую модель; в README указать, как перегенерировать.

### Новый вариант модели
1. Если модель одиночная — сначала превратить её в семейство: общий README и `src/` наверх, текущая модель становится одним из вариантов.
2. Добавить в общий генератор параметр для нового варианта. Проверить, что существующие варианты получаются из него без изменений — сравнить с их 3mf.
3. Сгенерировать 3mf и картинки нового варианта, написать его README, добавить в таблицу вариантов и в реестр.

### Доработка существующей модели
1. Прочитать `README.md` модели (и семейства, если это вариант) и историю версий.
2. Создать новую версию (копия предыдущей), внести изменения там.
3. Обновить картинки, README (актуальная версия, габариты, история версий) и реестр.

### Чего агент не делает без явной просьбы
- Не удаляет и не перезаписывает файлы существующих версий.
- Не создаёт ветки и не переписывает историю git.
- Не меняет структуру проекта и правила из этого файла. Если правило мешает — предлагает изменение пользователю.
