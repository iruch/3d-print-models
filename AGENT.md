# AGENT.md — модели для 3D-печати

Точка входа для любого агента. Прочитай этот файл целиком, прежде чем что-то делать в проекте.

## Назначение

Проект для разработки, хранения и доработки моделей для 3D-печати. Работа ведётся вместе с ИИ-агентом.

Модели делаются **для любого принтера**, на стол которого они помещаются, независимо от производителя. Свой принтер автора (Creality K1C) — только тот, на котором модели проверяются. Нельзя писать описания так, будто модель подходит только для K1C или только для одного слайсера.

Модели выкладываются **бесплатно для всех** по лицензии CC BY 4.0, поэтому репозиторий публичный. У популярных моделей есть варианты (например, органайзер на 2, 3 и 4 устройства), чтобы каждый выбрал подходящий. Описания пишем для человека со стороны: он должен понять, что это, подойдёт ли ему и как это напечатать, не читая код.

Цель: по любой модели в любой момент понятно — что это и зачем, как она выглядит и какого размера, из чего и как её печатать, из какого кода она получена, какая версия актуальная и чем версии отличаются.

Репозиторий: <https://github.com/iruch/3d-print-models>. Правила работы с ним — в разделе «Git». Локальная папка проекта по старой памяти называется `crealityk1c` — на работу это не влияет.

## Язык

**Всё на русском:** общение с пользователем, документация, комментарии в коде, сообщения коммитов. Латиница — только там, где без неё никак: имена файлов и папок (slug), идентификаторы в коде, технические термины и названия программ.

## Оборудование и окружение

- **Принтер автора** (на нём проверяются модели): Creality K1C — область печати 220 × 220 × 250 мм, закрытый корпус, директ-экструдер, закалённое сопло 0.4 мм, хотэнд до 300 °C, стол до 100 °C.
- **Слайсер автора:** Creality Print 7.3 (установлен локально).
- **Нити автора:** список материалов и цветов — в [FILAMENTS.md](FILAMENTS.md).
- **Другие принтеры:** справочник популярных принтеров с областью печати — в [PRINTERS.md](PRINTERS.md).
- **Node.js 24** — на нём скрипты из `tools/`.
- **Python** — только через `uv`, в систему не ставится. В начале каждого `.py`-генератора есть блок `# /// script` со списком зависимостей. Поэтому достаточно `uv run <скрипт>.py`: uv сам подтянет Python и библиотеки.

Заметки агенту по этой машине:
- `uv run` спотыкается о собственную ссылку на Python 3.14. Обход: указать интерпретатор явно — `uv run --python "$APPDATA/uv/python/cpython-3.14.8-windows-x86_64-none/python.exe" <скрипт>.py`.
- Если вывод Python идёт в pipe, выставлять `PYTHONUTF8=1`. Иначе кириллица и знаки вроде «×» падают с ошибкой кодировки cp1251.

- **slug** — имя латиницей в kebab-case, которое само говорит, что это. Номеров и ID нет. У варианта slug = slug семейства + суть варианта: `lil-solid-organizer-2-devices`.

## Одиночная модель и семейство

- **Одиночная модель** — одна папка `models/<slug>/` с `README.md` по шаблону [templates/MODEL.md](templates/MODEL.md). Код лежит внутри версии: `vN/src/`.
- **Семейство** — модель, у которой есть варианты (на разное число устройств, разного размера и т. п.):
  - `models/<семейство>/README.md` по шаблону [templates/FAMILY.md](templates/FAMILY.md). В нём общее описание, всё, что одинаково у вариантов (посадочные места, печать, исходники), и таблица вариантов с картинками.
  - `models/<семейство>/src/` — один параметрический генератор на все варианты. Вариант задаётся параметром командной строки, а не копией скрипта.
  - Каждый вариант — подпапка `<семейство>-<суть>/` со своим `README.md` (тот же шаблон MODEL.md, но короче: только то, что отличает вариант) и своими версиями `vN/`.
- Одиночная модель становится семейством, как только у неё появляется второй вариант.

## Что обязательно есть у каждой модели (и каждого варианта)

1. `README.md`: описание нормальным человеческим языком, **совместимость (принтеры и материалы)**, габариты, параметры печати, как получить файл, история версий.
2. В каждой версии `vN/`:
   - файл `<slug>-vN.3mf`;
   - код генерации, если модель сделана кодом: в `vN/src/` у одиночной модели, в `src/` семейства — у варианта;
   - картинки в `img/`:
     - `iso.png` — общий вид в 3D с подписью габаритов;
     - `front.png`, `left.png`, `right.png`, `top.png` — проекции спереди, слева, справа и сверху с размерами;
     - `filled.png` — модель с содержимым, если в неё что-то кладут или ставят (органайзеры, держатели, подставки). Это первая картинка в README: человек сразу видит, как вещь выглядит в деле;
     - `preview.png` — миниатюра из 3mf (`Metadata/plate_*.png`), если слайсер её туда положил.
3. Строка в [REGISTRY.md](REGISTRY.md).

### Картинки

Картинки делает скрипт, вручную их не рисуем. Если скрипт с чем-то не справляется, дорабатываем скрипт.

```bash
npm install --prefix tools          # один раз, ставит зависимости
node tools/render-3mf.mjs <папка модели>/vN/<slug>-vN.3mf <папка модели>/vN/img --name "<Название>"
```

Опция `--color "#RRGGBB"` задаёт цвет модели на картинках, например цвет нити, которой её печатают. Скрипт также выводит габариты, объём тела, нужный размер стола и принтеры из [PRINTERS.md](PRINTERS.md), на которые модель помещается. Всё это берём в README, а не считаем вручную.

#### Картинка с содержимым

- **Содержимое строит генератор модели**, а не скрипт картинок: только генератор знает, где какое гнездо. Для этого у генератора есть режим `--filled`. Он собирает сцену: сама модель плюс условные предметы на своих местах (устройства, пачки, кабель…). Каждый предмет — отдельный объект 3mf со своим цветом (`basematerials`, `displaycolor`).
- **Предметы рисуем упрощённо:** простые формы и спокойные цвета, без логотипов и попыток изобразить реальность. Размеры берём из тех же параметров, что и гнёзда. Если реальный размер неизвестен (например, высота пачки), ставим примерный и помечаем это в коде.
- **Рендер:** `node tools/render-3mf.mjs <сцена.3mf> <папка модели>/vN/img --filled --name "<Название>"`. Получится `filled.png`: общий вид чуть сверху, сама модель серая, как на остальных картинках, а предметы — в своих цветах.
- **Сцена — не модель для печати.** Её не коммитим (`*-filled.3mf` в `.gitignore`), всегда можно получить заново.

### Совместимость

Человек открывает модель и должен сразу понять, напечатает ли он её на своём принтере и своей нитью. Поэтому в README каждой модели и варианта есть раздел «Совместимость»:

- **Нужный стол.** Размер в плане с запасом 5 мм на сторону и высота печати. Пишем, что модель можно повернуть на столе на 90°.
- **Принтеры.** Таблица: на каких принтерах из [PRINTERS.md](PRINTERS.md) модель помещается, а на каких нет. Список берём из вывода `render-3mf.mjs`. Отдельной строкой — на чём модель проверена печатью.
- **Материалы.** Таблица: какие нити подходят, какие не рекомендуются и почему. Отдельно — какой нитью модель проверена. Типовая логика:
  - PLA — для вещей в комнате без нагрева и нагрузки;
  - PETG — прочнее, терпит тепло до ~70 °C;
  - ABS/ASA — только в закрытом принтере, иначе большие плоские детали отрывает от стола;
  - TPU — для гибких деталей, для жёстких корпусов не подходит.
- **Слайсер.** Наши 3mf содержат только геометрию, без настроек конкретного принтера. Поэтому они открываются в любом слайсере: Creality Print, Bambu Studio, OrcaSlicer, PrusaSlicer, Cura. Настройки печати человек берёт у своего принтера, а мы даём рекомендации (слой, стенки, заполнение, поддержки).
- **Посадки.** Если в модели есть посадки с зазором, предупреждаем: на другом принтере и другой нити зазоры могут сесть иначе. Советуем сначала напечатать пробник, если он есть.

Если у семейства совместимость общая, подробности пишем в README семейства, а в README варианта — только то, что зависит от его размера (стол и принтеры).

## Версионирование

- Версии — целые числа: `v1`, `v2`, `v3`… У каждого варианта семейства своя нумерация.
- **Версию получает только успешная модель:** напечатанная и проверенная в деле, статус «рабочая». Неудачные попытки версиями не становятся и в репозитории не остаются.
- Модель, пришедшая в проект, всегда начинается с `v1` — даже если до проекта у неё были свои номера (например, файл назывался `_v5`). С неё всё и начинается: прошлые итерации в историю не переносим.
- Новый вариант — это не новая версия: он начинается со своей `v1`.
- **Пока результата нет, номер не меняется.** Вся работа идёт в папке будущей версии: у новой модели это `v1`, у доработки успешной `vN` — `vN+1`. Неудачная печать не даёт нового номера: правки идут в ту же папку, её файлы перезаписываются. Следующий номер нельзя заводить и нельзя обещать, пока текущий не стал успешным.
- Если доработку бросили и успешной она не стала, её папку удаляем. Актуальной остаётся последняя успешная версия.
- Как только версия стала успешной, она заморожена. Следующие изменения геометрии или настроек идут в новую папку `vN+1/`, созданную копированием предыдущей.
- Если поменялся общий генератор семейства, новая версия появляется у тех успешных вариантов, у которых изменилась геометрия. Код старых версий остаётся в истории git.
- Правка только текста документации или кода без изменения геометрии — не новая версия.
- Успешные версии **не удаляются и не перезаписываются**. Git хранит историю, но версии всё равно лежат отдельными папками: любую можно сразу открыть в слайсере и сравнить с другой, не копаясь в истории коммитов.
- Неактуальную модель целиком переводим в статус «архив», а не удаляем.
- В `README.md` модели — таблица «История версий»: что изменилось и почему и как версия показала себя в деле. Неудачные попытки своих строк не получают. Если попытка объясняет, почему деталь устроена именно так, пишем об этом в «Заметках», без номеров версий.

### Статусы

| Статус | Значение |
|---|---|
| черновик | успешной ещё не стала: не печаталась или печать не удалась, идут правки |
| на проверке | напечатана, проверяется в деле, успешной ещё не признана |
| рабочая | успешная версия: проверена в деле, можно печатать |
| архив | больше не используется, хранится для истории |

## Реестр

[REGISTRY.md](REGISTRY.md) — одна строка на каждую модель, которую можно напечатать: одиночную модель или вариант семейства. В строке: название со ссылкой, кратко назначение, актуальная версия, нужный стол, подходящие материалы, статус, дата обновления. Реестр обновляется в том же шаге, что и модель — они не должны расходиться.

## Git

- Работает один человек. Ветка одна — `main`. Других веток, pull request'ов и ревью нет.
- Агент коммитит и **сразу пушит в `main`** по завершении каждой задачи: новая модель, новая версия, правка документации или скриптов. Отдельно спрашивать разрешения на коммит и пуш не нужно.
- Один коммит — одно законченное изменение. Файлы модели, картинки, README и строка реестра идут в одном коммите.
- Сообщение коммита — на русском, в формате `<область>: <что сделано>`. Область — папка модели, варианта или семейства, `документация` или `инструменты`. Если нужно объяснить «почему», то после пустой строки идёт тело сообщения. Примеры:
  - `phone-stand: добавлена v1`
  - `lil-solid-organizer: варианты на 2 и 3 устройства`
  - `lil-solid-organizer-4-devices: v2 — отсек под кабель шире на 5 мм`
  - `инструменты: рендер видов с размерами`
- Историю не переписываем: никаких `push --force`, `rebase` и `commit --amend` для уже запушенных коммитов.
- В git не попадает: содержимое `inbox/`, временные файлы, `__pycache__`, виртуальные окружения, `node_modules`.
- GitHub не принимает файлы больше 100 МБ. Если файл больше 50 МБ, агент предупреждает пользователя до коммита.
- Репозиторий публичный: в него не кладём ничего личного (пароли, адреса, документы).

## Контракт работы агента

### Пластик не экономим
Прочность, точность и надёжность важнее расхода нити. Не убираем и не уменьшаем элементы, чтобы сэкономить пластик, и не советуем редкое заполнение там, где деталь несёт нагрузку.

### Общение
- Агент не придумывает назначение модели, материал или результат печати. Чего не знает — спрашивает. Неподтверждённое помечает как неподтверждённое.
- После любой работы агент коммитит и пушит её (см. «Git») и коротко отчитывается: что создано или изменено, какие файлы, что осталось открытым.
- Беспрекословного повиновения пользователь не ждёт. Агент и пользователь равны, ошибаются оба. Если пользователь действительно не прав, агент спорит и старается его вразумить: прямо говорит, что не так и почему.
- Мат в переписке — обычная речь: так люди лучше понимают друг друга. Агент не принимает его на свой счёт и сам может сказать прямо и резко, если пользователь делает что-то не то.

### Советы
Ошибочный совет стоит часов работы принтера и пластика, поэтому его проверяют до выдачи, как и модель.

1. **Обход всегда с условием.** Говорим, когда он безопасен, чем это проверить и что будет, если условие не выполнено. Если условие назвать не можем, значит, обход не понят, и мы его не советуем.
2. **Один удачный случай не правило.** Обход сработал при конкретных обстоятельствах. Прежде чем повторить его или записать в заметки, выясняем, какие из них обязательны.
3. **Совет живёт дольше разговора.** Пользователь применит его через день, сам и при других условиях. Поэтому перед советом проверяем: что будет, если сделать это в самый неудачный момент.
4. **Что можно проверить, проверяем сами и до совета.** Принтер, слайсер и файлы агенту доступны, перекладывать проверку на пользователя нельзя. Если проверить нельзя, прямо так и пишем.
5. **Опасный совет исправляем сразу везде,** где он записан: в заметках, документации и ответах.

### Отправка на печать
Creality Print отправляет файл без полосы прогресса, поэтому идущая загрузка и зависшее окно выглядят одинаково. Файл виден в списке принтера с первой секунды загрузки, и принтер запустит его неполным: допечатает до обрыва и напишет «завершено», без ошибки. Так оборвалась первая пробная печать кейса-микрофона.

- Пока файл не сверен, его не запускают с экрана принтера, а окно отправки не отменяют и не закрывают. Отмена оставляет на принтере обрезанный файл.
- Загрузка на K1C автора идёт около 0,55 МБ/с. После неё слайсер запускает печать примерно через 25 секунд. Файл на 25 МБ стартует чуть больше чем через минуту.
- Если окно затупило, пользователь пишет агенту. Агент сверяет файл и только после этого говорит, можно ли запускать.
- Сверка идёт через API принтера на порту 7125:
  - размер файла в `/server/files/directory?path=gcodes` равен размеру файла слайсера в `%TEMP%\crealityprint_model\<дата>\<время>\Metadata\`;
  - файл на принтере кончается блоком настроек с `; CONFIG_BLOCK_END`;
  - размер из `/server/files/metadata` не годится: он снят в начале загрузки.
- Выдавая файл для долгой печати, агент сразу напоминает эти правила.
- Обрезанный файл больше не запускаем. Кнопка «Повтор» на экране принтера запустит его снова.

### Новая модель (файлы в `inbox/` или в чате)
1. Изучить файлы: габариты, число объектов и пластин, настройки печати из 3mf (материал, слой, заполнение, поддержки), код, если он есть.
2. Показать пользователю, что удалось понять, и **спросить**: что это, для чего, где и как используется, каким материалом и цветом печатать, были ли проблемы.
3. Придумать slug, создать `models/<slug>/v1/`, перенести туда файлы (из `inbox/` — переносом, не копией).
4. Сгенерировать картинки видов.
5. Написать `README.md` по шаблону и добавить строку в реестр.

### Новая модель, которую разрабатывает агент
1. Уточнить задачу: назначение, ключевые размеры, ограничения, материал.
2. Написать генератор (параметры — в начале файла, с комментариями; блок `# /// script` с зависимостями), получить модель, сделать картинки.
3. Документировать так же, как любую модель; в README указать, как перегенерировать.

### Копия существующей детали
1. Цель — воспроизвести оригинал как есть. Источник формы — ссылка и фото от пользователя, и только они: фото похожих деталей не подмешиваем.
2. Никаких своих упрощений и «улучшений»: не срезаем, не усиливаем, не убираем рёбра и стенки ради удобства печати. Если для печати нужно отступить от оригинала, сначала предлагаем это пользователю и ждём ответа.
3. Сверяем модель с оригиналом рядом на одной картинке, каждый узел крупно. Сначала смотрим, как устроена и для чего нужна каждая деталь оригинала, потом моделируем.

### Новый вариант модели
1. Если модель одиночная — сначала превратить её в семейство: общий README и `src/` наверх, текущая модель становится одним из вариантов.
2. Добавить в общий генератор параметр для нового варианта. Проверить, что существующие варианты получаются из него без изменений — сравнить с их 3mf.
3. Сгенерировать 3mf и картинки нового варианта, написать его README, добавить в таблицу вариантов и в реестр.

### Доработка существующей модели
1. Прочитать `README.md` модели (и семейства, если это вариант) и историю версий.
2. Если текущая версия успешная, создать новую (копия предыдущей) и менять её. Если ещё нет, править её же: неудачная печать новой версии не даёт.
3. Обновить картинки, README (актуальная версия, габариты, история версий) и реестр.

### Чего агент не делает без явной просьбы
- Не удаляет и не перезаписывает файлы успешных версий.
- Не создаёт ветки и не переписывает историю git.
- Не меняет структуру проекта и правила из этого файла. Если правило мешает — предлагает изменение пользователю.
